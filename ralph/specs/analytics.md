# Analytics — PRD

**Status:** proposed · **Route:** `/analytics` · **Sidebar:** Signals, after Metrics
**Owner:** leo · **Written:** 2026-08-23

Guard measures what the backend did. It cannot yet answer *what a person did* —
which page they landed on, whether they pressed the thing the page exists to
make them press. This adds that, as a fourth signal that is not an OTLP signal:
a two-kilobyte script, one narrow public door, and one page whose whole content
is a grid of **actions per URL**.

The organising idea, stated once: **the URL is the group, an action is a column.**
Everything below follows from that sentence.

---

## 1. Why not the tools that exist

### Google Analytics 4

GA4's model is *event with parameters* — every interaction, including a page
view, is a named event carrying up to 25 parameters, and `page_location` /
`page_path` are parameters like any other. Reports are then built by grouping
events by a parameter. Four event classes: automatically collected
(`page_view`, `session_start`, `first_visit`, `user_engagement`), enhanced
measurement (scroll, outbound click, file download, form interaction — ten
names, zero code), recommended (fixed schema so Google can pre-build the
report), and custom.

**What is worth stealing:** one event table, name plus a small bag of
parameters, and a sharp line between events that arrive for free and events
somebody wrote. The free tier is what makes the tool useful on day one instead
of after a week of instrumentation.

**What is not:** 25 parameters per event, a parameter that must be registered
as a "custom dimension" before it appears in a report, and a session model with
enough rules to need its own documentation page.

### Plausible / Umami

The lightweight end. A ~2 KB script, no cookies, no consent banner, a custom
event as a *name plus a flat `props` object of strings*. Plausible puts events
in ClickHouse; Umami runs one Node process against Postgres and shares a 2 GB
VPS with the site it measures. Umami's shape is the one guard should match —
guard already is a single binary over SQLite, and the traffic a guard instance
watches is a company's product, not a newspaper.

**What is worth stealing:** the script size, the no-cookie session, the flat
string-only props, and *goals* — the small hand-picked set of events that get a
column, as opposed to everything that was ever fired.

### PostHog

Autocapture: bind one delegated listener and record every click, input change
and form submit on the page. Then **Actions** — a named rule over those raw
events, usually a CSS selector generated by pointing at the element in a visual
toolbar.

The tradeoff is well known and worth quoting, because it decides guard's
design: *autocapture is for discovery, custom events are for decisions — if
your metric depends on an autocaptured click, it breaks the moment somebody
changes the CSS.*

**What is worth stealing:** the discovery/decision split.
**What is not:** storing CSS selectors in the analytics tool. A selector in
guard's database is a copy of somebody else's markup that guard cannot keep
correct, and it silently reads zero on the day the markup changes — which is
guard's cardinal sin (see "unmeasurable is silent, never zero"). Guard's answer
puts the selector back in the markup: `data-guard-track="signup_click"`.

### HyperDX / ClickStack

The nearest neighbour architecturally: browser events land in their own table
(`hyperdx_sessions`, the log schema with no TTL) and correlate to the backend
through two join keys — `TraceId`, and a `rum.sessionId` materialised as a
column on the traces table with a bloom filter so the join is not a scan.

**What is worth stealing:** the session id is the join key, and it earns a
materialised column rather than living only inside a JSON blob. Guard already
has the generated-column pattern for exactly this (`indexedAttributes` in
`internal/telemetry/views.go`).

**What is not:** session replay. It is a different product with a different
storage budget.

## 2. What guard already has

This is not a greenfield feature. Four things exist and must be reused rather
than paralleled:

| exists | reused as |
|---|---|
| `/v1/rum/traces`, `/v1/rum/logs` (`internal/ingest/rum.go`) — public door, origin allowlist, 256 KB body, 120/min per address, identity assigned not accepted | the analytics door is a third path on the same door, same config struct, same limiter |
| `GUARD_RUM_ORIGINS` | enables analytics too. **No new environment variable.** |
| `settings` table + Settings → Data storage | where analytics retention is typed, beside the other two numbers |
| `client/public/store.js` | the page's data path, like every other page |
| `internal/notify` | where an analytics alert leaves, when it exists |

The rule the door already keeps — *the service identity is assigned by guard,
never accepted from the payload* — is the reason this can be public at all, and
it applies unchanged.

## 3. Goals and non-goals

**Goals**

1. Answer "what do people do on this page" for any page, with no query to
   compose and no chart to configure.
2. Be installable in one line of HTML, with nothing to `npm install` and no
   build step on the customer's side.
3. Cost nothing measurable on the write path, and be honest about cardinality
   rather than quietly exploding the events table.
4. Keep history longer than telemetry does, without keeping raw rows.
5. Add zero `GUARD_*` variables.

**Non-goals for v1** — each of these is a whole product, and shipping the grid
first is what makes them answerable later:

session replay · funnels and conversion paths · cohorts and retention curves ·
identified users (`identify()`, user profiles) · revenue and ecommerce ·
attribution modelling · A/B tests · heatmaps · a visual toolbar for picking
elements.

**Explicit non-goal, permanently:** guard will not store CSS selectors, and
will not autocapture every click. See PostHog, above.

## 4. The model

Four nouns. Two are stored by a person, two are counted by the machine.

### 4.1 Path — the group

A path is the normalised URL, and normalisation happens **in the browser,
before the beacon leaves**:

- query string and hash dropped (except three UTM keys, §4.4)
- trailing slash removed, `/` kept as `/`
- lowercased, truncated to 200 chars

Then, in guard, **path rules** collapse dynamic segments:
`/users/*` → `/users/:id`. Stored rows (`analytics_path_rules`, ordered, first
match wins), editable on the page, part of the backup — they are configuration.
A rule is applied at ingest, so it shapes what is stored rather than what is
displayed; changing one does not rewrite history, and the page says so.

**The cardinality cap is load-bearing.** A hard ceiling of distinct paths per
day (default 1,000); everything past it rolls into a single `(other)` row whose
count is real and whose name says what happened. Every analytics product that
has ever been run against a site with unbounded URLs has learned this, and a
cap that announces itself beats a table that grows until SQLite is slow.

### 4.2 Action — the column

An action is a **name**, nothing more: `signup_click`, `checkout_start`,
`docs_search`. Guard **discovers** action names from what arrives — they are
not declared in advance, because a tool that requires registration before it
records is a tool people give up on mid-instrumentation. Discovery is capped
(default 200 distinct names); past the cap a name is **refused, never
truncated or renamed**, and the refusal count is shown on the page. A silently
merged action is worse than a missing one.

Discovery and decision are then split the way PostHog splits them, but with the
rule in guard rather than in a selector: an action can be **pinned**. Pinned
actions are the grid's columns, in a stored order. Unpinned actions still count
and still appear when a path row is opened — they are the discovery half.

`page_view` is reserved, always counted, never a column (it is the Views
column).

### 4.3 Session — the denominator

**Guard counts sessions, and says the word "sessions" everywhere it means
sessions.** Not users, not visitors, not people.

A session id is 16 random bytes in `sessionStorage`, created on first event and
expired after 30 minutes of inactivity (GA4's boundary, and the only part of
GA4's session model worth copying). **No cookie. No IP hash. No fingerprint.**

That is a deliberate, statable weakness: one person in two tabs is two
sessions, and tomorrow they are a new session. The alternative — Plausible's
daily-rotated salted hash of IP + user agent — requires storing something
derived from an address that guard's RUM door currently discards on principle,
and buys a number that is still an estimate. A metric that is exactly what it
says beats one that is approximately what somebody wanted.

The session id is also the **join key**, following HyperDX: it goes into the
analytics rows *and* is emitted as `rum.session_id` on browser spans, so a path
with a bad conversion rate can be walked into `/traces`. It earns a generated
column (an entry in `indexedAttributes`, which is the only change that needs).

### 4.4 Source — where they came from

Three fields, extracted client-side before the query string is dropped:
`utm_source`, `utm_medium`, `utm_campaign`, plus the **referrer host** (host
only — the full referrer URL is somebody else's private path). Own rollup, own
list on the page. Three fields rather than a props system, because attribution
is the one thing every analytics install wants and the cheapest possible
version of it is four strings.

## 5. Storage

Three tables and one rule: **the rollup is the truth, the raw feed is a
courtesy.**

```
analytics_events    raw, short retention (the telemetry retention), the live feed
analytics_rollup    (day, path, action) → events, sessions        ← survives
analytics_seen      (day, path, action, session_id)               ← exactness, then purged
analytics_sources   (day, path, source, medium, campaign, referrer_host) → sessions
analytics_actions   (name, pinned, position, first_seen, last_seen)   ← configuration
analytics_path_rules (pattern, replacement, position)                 ← configuration
```

**Why a rollup at all.** `events` is capped (`max_events`, default 1M) and
swept by `retention_hours`. Analytics that vanish at the cap are analytics
nobody trusts — the question is always "versus last month". The rollup is one
row per (day, path, action), which for a real product is thousands of rows a
month, not millions.

**How sessions stay exact without HyperLogLog.** On each event:

```sql
INSERT OR IGNORE INTO analytics_seen(day, path, action, session_id) VALUES(?,?,?,?);
-- changes() == 1 means this session had not done this on this day
INSERT INTO analytics_rollup(day, path, action, events, sessions) VALUES(?,?,?,1,?)
  ON CONFLICT(day, path, action) DO UPDATE SET events = events + 1, sessions = sessions + ?;
```

Exact distinct counts, no sketch, no approximation to explain on a dashboard.
`analytics_seen` is the only table that grows with traffic rather than with
content, and it is purged behind the rollup (default: 7 days of `seen`, 90 days
of rollup) — after which the counts stand and cannot be recomputed, which is
the honest trade and belongs in the docs.

Retention is **two rows in `settings`** (analytics rollup days, analytics raw
hours), edited on Settings → Data storage beside the two that are there. Not
environment variables: the catalogue is twenty-two and stays twenty-two.

**Backup.** `analytics_actions` and `analytics_path_rules` join `backupTables`
— they say how guard is configured. `analytics_events`, `analytics_rollup`,
`analytics_seen` and `analytics_sources` join `backupExcluded`, written out
beside them, for the same reason logs are: they are the part that grows and
they say nothing about configuration.

**Writes.** Every write goes through the store's single writer, like everything
else, and the rollup UPSERT is batched per request (one transaction per beacon,
not per event).

## 6. Ingest

### The door

`POST /v1/rum/events` — a third path on the browser door in
`internal/ingest/rum.go`, mounted by the same `RegisterBrowser`, gated by the
same `GUARD_RUM_ORIGINS`, sharing the same rate limiter, same 256 KB budget,
same CORS preflight, same "no Origin means a relay, allow it" rule. The
deployment advice in `docs/browser-telemetry.md` — relay through the app you
already expose — applies unchanged and needs one more path in the example.

**Not OTLP.** The OTLP JS exporter plus the web tracer is tens of kilobytes for
a payload that is a name and a path. This door takes guard's own JSON, and the
brevity is the point:

```json
{
  "s": "6f2a9c1d4e8b7a30",
  "p": "/pricing",
  "u": {"s": "google", "m": "cpc", "c": "spring"},
  "r": "news.ycombinator.com",
  "e": [
    {"n": "page_view", "t": 1755900000123},
    {"n": "signup_click", "t": 1755900004411, "d": {"plan": "team"}}
  ]
}
```

Rejected at the edge, before decoding where possible: more than 50 events in a
batch, an action name over 64 chars or outside `[a-z0-9_.-]`, more than 8 props
per event, a prop value over 200 chars. Rejections are counted and surfaced —
`GET /api/analytics/health` — because a tracker that is being silently dropped
is the failure mode people take weeks to notice.

### The script

`GET /v1/rum/track.js` — served by guard, `go:embed`ed from
`internal/ingest/track.js`, cached hard, public. Deliberately **not** under
`client/public/`: that directory is the dashboard's own JavaScript and each
file there needs a Tailwind `@source` line, and the tracker is neither. It
lives beside the endpoint it posts to.

Budget: **under 2 KB minified, zero dependencies, no build step.** Vanilla ES5-
safe, one `<script defer>` tag.

```html
<script defer src="https://guard.example.com/v1/rum/track.js"
        data-endpoint="/api/telemetry/events"></script>
```

What it does:

- fires `page_view` on load, and again on `pushState` / `replaceState` /
  `popstate`, so a single-page app works with no extra call
- exposes `guard.track(name, props)`
- binds **one** delegated `click` listener and fires the action named by the
  nearest `[data-guard-track]` ancestor. The selector lives in the markup,
  where the person who changes the markup can see it
- batches, flushing on a 5-second timer and on `visibilitychange:hidden`
  through `navigator.sendBeacon` — the only flush that survives a tab closing
- writes nothing but the session id, to `sessionStorage`
- does nothing at all when `navigator.doNotTrack === "1"`, and is a no-op if
  the endpoint 4xxs twice in a row

## 7. The page

`/analytics`, `client/pages/analytics/index.client.templ`, with
`client/public/analytics.js` as its renderer and `store.js` as its data path
(and therefore a new `@source` line in the `css` target — the step that
silently does nothing if skipped).

Three bands. The middle one is the feature.

### The strip

Sessions · Page views · Views per session · Actions per session, over the
selected window, each with the change against the previous window of equal
length. The window control is the dashboard's existing one.

### The grid — actions per URL

One row per path, in fixed columns, ordered by views:

```
  PATH                    VIEWS   SESSIONS   signup_click   checkout_start   docs_search
  /                       12,430     8,102     412  3.3%          —              —
  /pricing                 3,204     2,884     289  9.0%         104  3.2%       —
  /docs/:page              9,981     4,120       —              —              1,204 12.1%
  (other)                    412       388       —              —              —
```

Each pinned action is a column carrying **count and rate**, where the rate is
sessions-that-did-it over sessions-that-saw-the-page — the conversion number,
which is the only reason the column is there. A dash, never a zero, where the
action was never seen on that path: guard's rule everywhere is that an empty
window is silence rather than zero, and `0.0%` next to a column that page has
no button for is a lie in a fixed-width font.

Fixed columns for the same reason `/registries` and `/storage` are lists — that
alignment is what makes the row that is unlike the others findable. Sortable by
any column. Header cells reorder and unpin.

### The fold

A path row opens onto what a row has no width for:

- a sparkline of views and sessions over the window (an existing renderer in
  `charts.js`)
- **every** action on that path, pinned or not — the discovery half — each with
  a pin button, which is how a column gets created
- top referrer hosts and campaigns into that path
- a link into `/traces` filtered to that path's sessions, which is the whole
  reason the session id is a join key

### Elsewhere on the page

**Actions** — the full discovered list with counts, first and last seen, pin
and delete. A deleted action stops being counted and its rollup rows go; the
dialog says so.

**Paths** — the rules, with a live preview against the last 100 distinct paths
seen, so a rule is proved before it is stored. Same shape as every other
prove-before-store in guard.

**Install** — the script tag with this instance's URL already in it, a copy
button, and the one-paragraph relay note from `docs/browser-telemetry.md`. The
band disappears once the first event arrives.

### Empty and off states

- `GUARD_RUM_ORIGINS` unset → the page says analytics is off, names the
  variable, and links to Settings → Configuration. Configured is on,
  unconfigured is off, and the page says which.
- Configured, nothing received → the Install band, full width, alone.

## 9. Phases

Each phase ends somewhere shippable.

**Phase 1 — the spine.** The door, the script, the three tables, the rollup
writer, `GET /api/analytics/paths`, the page with the strip and the grid, the
sidebar row, the install band. Pinning exists but the first three discovered
actions are auto-pinned so the grid is never empty. *This is the demo.*

**Phase 2 — the fold.** Sparkline, full action list per path, sources rollup
and the referrer/campaign lists, the raw feed, `analytics_health`.

**Phase 3 — the controls.** Path rules with live preview, action admin
(pin, reorder, delete), retention on Settings → Data storage, backup wiring,
`docs/analytics.md`.

**Phase 4 — the join and the watch.** `rum.session_id` as an indexed
attribute and the link into `/traces`. Analytics as a source the view compiler
can read, which gets alerts for free through `internal/viewalerts` rather than
building a second alerting path — the rule guard already keeps.

## 10. Risks

**Ad blockers.** Every list blocks paths matching `analytics`, `track`, and the
hostnames of the big vendors. Mitigated by the relay deployment already
documented: the browser posts to the customer's own origin. The install band
should recommend the relay first and the direct URL second, and say why.

**Write amplification.** Every browser event is up to three writes (raw, seen,
rollup) against a single-writer SQLite. Mitigated by one transaction per
beacon, batching in the tracker, and the raw table being the first thing to
make optional if a busy instance shows contention. Needs a benchmark beside
`internal/ingest/benchmark_test.go` before Phase 1 ships.

**`analytics_seen` growth.** Bounded by (sessions × distinct paths × distinct
actions per day), which is fine for a product and not fine for a content site
with a thousand pages and a hundred thousand sessions. The path cap bounds one
factor and the seen-retention bounds the other; a counter on the health
endpoint makes it visible before it is a problem.

**Rollups are irreversible.** Once `analytics_seen` is purged, session counts
for those days cannot be recomputed under a new path rule. Say it in the docs,
say it in the path-rule dialog.

**"Sessions" gets read as "users".** Mitigated by never writing the other word,
anywhere, including tooltips.

## 11. Open questions

1. **Auto-pin heuristic.** Phase 1 auto-pins the first three actions seen. Is
   "most frequent in the last 24h" better than "first seen"? First-seen is
   deterministic and explainable; most-frequent is more often right.
2. **`(other)` path bucket.** Should a path that has fallen into `(other)`
   graduate back out when the cap frees up, or is that a moving-history problem
   worse than the truncation?
3. **Do props ever get a column?** They are stored and shown in the feed in
   Phase 2 and grouped by nothing. Grouping a prop is Plausible's "custom
   properties" and one more index — worth it, or the first step onto the GA4
   custom-dimension treadmill?
4. **Scroll depth and time on page.** Two events GA4 gives free and everyone
   asks for. Both need a `visibilitychange` timer in the tracker and both cost
   bytes in a 2 KB budget. In or out?
5. **Does the raw feed earn its table**, or is `analytics_events` a debugging
   aid that should live behind a "keep raw events" toggle that is off by
   default?
